# 自然叙述规范 v1

本文件约束默认交付给用户的专题解读。目标是让每个判断同时具备术语、规则机制、现实含义和边界，但不把它写成模板报告或后台审计单。

## 交付面只有正文

默认回答只输出连贯的自然段落。不要自动附加标题、步骤编号、来源区、告警区、声明区、技术附录或“还想看什么”的菜单。

`interpretation.json` 中的 `facts`、`evidence`、`reason`、`caveat`、`warnings`、`disclaimers`、`followupOffers` 都是写作和审计输入，不是默认展示字段。它们只在用户明确要求查看盘面、计算详情或推理来源时按需展开。

## 每个判断的内部推理链

先在内部完成下列链路，再写成自然语言：

```text
盘面事实（claim / evidence）
  → 规则机制（reason / 版本化 ruleset）
  → 当前问题中的现实倾向、场景或建议
  → 适用条件、输入精度或流派限制（caveat / warnings）
```

不得跳过前两项直接写结论，也不得把一个没有对应 `evidence.ref` 或 `ruleId` 的新盘面事实写入正文。

## 术语要自然落地

专业名词可以、也应当出现在正文中；它必须在同一句或紧接着的句子里说明对当前问题的作用。

不要写：

> 官杀旺，事业压力大。

可以写：

> 官杀在这里较集中，指向规则、责任和外部评价会更容易成为工作主题。目标清楚、权责稳定时，这股压力能推着你把事做深；要求反复变化却没有资源支持时，消耗感会更明显。

不要写：

> 七宫主受克，感情不顺。

可以写：

> 第七宫主星与土星形成紧密关系，亲密关系里的承诺、距离感和责任分配会被反复放大。你未必不愿意靠近，只是更需要把期待、时间和边界说清楚，才不容易把沉默误读成冷淡。

## 不使用固定句式

可以按事实选择因果、对比、条件、时间或跨体系交叉的表达方式。语言节奏可以变化，事实、证据和限制不能变化。

- 因果：月令决定日主在季节中的基础力量，因此……
- 对比：表面上像是犹豫，但这个结构更在意……
- 条件：在规则清楚时容易成为优势；在标准反复变化时则……
- 时间：这个阶段突出的是某类议题，不承诺发生某一件事。
- 交叉：八字与西占都触及同一主题；若证据不同，则说明差异，不制造共识。

不要使用“讲人话”“专业依据”“结论如下”“声明”“风险提示”“引擎警告”等栏目化语言。

## 告警和边界的自然转写

只有当限制会改变当前问题的判断时才提及它。不要展示 warning 名称、错误代码、provider、规则版本、事实编号或来源路径。

| 内部情况               | 默认写法                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| 出生时间未知或误差较大 | 出生时间若前后相差较大，上升、宫位或时柱相关的判断可能会变化；以下更侧重对这一误差不敏感的结构。 |
| 某体系无法计算         | 当前资料不足以支持这一层面的判断，因此不作延伸推断。                                             |
| 靠近分类边界           | 这个位置靠近分界，时间稍有调整时分类可能不同，不把它当成唯一依据。                               |
| 流派分歧               | 这里不同流派采用的口径并不完全一致，因此只保留它们共同支持的部分。                               |

不受当前问题影响的内部 warning 不显示。禁止固定免责声明页脚；传统文化、非科学预测和重大决定的边界由产品入口说明。涉及健康、法律、投资、生命安全或重大关系决定时，只在对应段落中给出最小必要的自然提示。

## 关系与合盘

只能描述互动模式、需要、摩擦条件和可执行的相处建议。不得写“注定在一起”“必分手”“必然结婚”“命定伴侣”，也不得用任何同义表达替代。

若需要说明边界，融入相关段落，例如：

> 这些结构更适合帮助你们识别靠近与卡住的方式；关系是否走得长远，仍取决于沟通、边界和双方当下的选择。

## 内部来源记录（默认不展示）

每个段落应保留以下追踪信息，供测试、审计和用户主动追问时使用：

```ts
type NarrativeTrace = {
  paragraphId: string;
  factRefs: string[]; // InterpretationFact.evidence[].ref
  ruleRefs: string[]; // bazi-rule/... 或其他版本化规则引用
  rulesets: string[]; // 当前结果中的 ruleset id + version
  mechanism: string; // reason 的受控摘要
  limitations: string[]; // caveat / 当前问题相关 warnings
  allowedClaims: string[]; // 本段可写的结论
};
```

来源优先级固定为：计算出的 `ChartBundle` 事实 → 版本化 ruleset → ADR / 来源矩阵 → provider/provenance。宿主模型只能组织这些材料，不能新增盘面事实、规则或事件承诺。

## 交付前检查

生成完成后，对默认正文运行：

```bash
node scripts/ming-chart.mjs lint-reading --input-file draft.md --channel topic
```

`ok: true` 才可交付。它会阻止后台标签、原始来源标识、固定页脚、自动追问、空话、重复和越界断言。它不能证明语义正确性；输出仍必须与内部 `NarrativeTrace` 对照。

用户明确要求“依据是什么”“看原始盘面”“计算设置是什么”时，单独提供技术详情，而不是把技术字段混进默认正文。
